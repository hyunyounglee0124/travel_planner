
## 1. REST API 의 요청/응답 구조와 GET/POST 의 차이

**한 줄 요약**: 클라이언트가 `메서드 + URL + 헤더 + (본문)` 으로 요청하면, 서버가 `상태코드 + 헤더 + 본문(JSON)` 으로 응답한다. GET 은 "조회", POST 는 "데이터를 보내서 처리/생성" 이다.

### 요청(Request)의 구성
| 요소 | 의미 | 이 프로젝트 예시 |
|---|---|---|
| 메서드 | 무엇을 할지 | Kakao 검색 `GET`, OpenAI `POST` |
| URL(엔드포인트) | 어떤 자원인지 | `https://dapi.kakao.com/v2/local/search/keyword.json` |
| 쿼리 파라미터 | URL 뒤 `?key=value` 로 붙는 조건 | `query=제주 맛집&category_group_code=FD6&size=5` |
| 헤더 | 부가 정보, **인증** | `Authorization: KakaoAK {키}`, `Authorization: Bearer {키}` |
| 본문(Body) | 서버에 보낼 데이터(JSON) | `{"model": "...", "messages": [...]}` |

### 응답(Response)의 구성
| 요소 | 의미 |
|---|---|
| 상태코드 | 2xx 성공 / 4xx 클라이언트 잘못(401 인증, 403 권한, 404 없음, 429 한도) / 5xx 서버 잘못 |
| 본문 | 대부분 JSON. Kakao 는 `documents` 배열, OpenAI 는 `choices[0].message.content` |

### GET vs POST
| | GET | POST |
|---|---|---|
| 목적 | 자원 **조회** | 데이터를 보내 **처리/생성** 요청 |
| 데이터 위치 | URL 쿼리 파라미터 | 요청 본문(Body) |
| 길이/형태 | 짧은 조건 위주 | 긴 프롬프트, 중첩 JSON 가능 |
| 멱등성 | 같은 요청 → 같은 결과(서버 상태 안 바꿈) | 호출할 때마다 새 처리(새 응답 생성, 과금) |
| 이 프로젝트 | 장소 검색: "제주 맛집 목록 주세요" | LLM: "이 긴 프롬프트로 답을 생성해 주세요" |

LLM 이 POST 인 이유: 프롬프트가 길고 구조화된(JSON) 데이터이며, 호출할 때마다 새로운 생성 작업이 일어나기 때문입니다.

**코드에서 보기**: `http_request()` 가 모든 호출의 공통부입니다. `PlaceSearcher._kakao()` 는 `params=` 로 GET,
`LLMClient._openai()` 는 `json_body=` 로 POST 를 보냅니다.

## 2. LLM 출력을 JSON 으로 구조화해 다음 단계 입력으로 쓰는 흐름

**한 줄 요약**: LLM 의 자유로운 문장 대신 "정해진 키를 가진 JSON" 을 받으면, 프로그램이 `rec["recommended_city"]` 처럼 값을 꺼내 지도 API 의 검색어로 바로 넘길 수 있다.

### 왜 JSON 이어야 하나
"3월엔 제주가 좋아요! 유채꽃이…" 같은 문장에서는 프로그램이 도시 이름을 안정적으로 뽑을 수 없습니다.
`{"recommended_city": "제주", ...}` 이면 키 하나로 정확히 꺼낼 수 있습니다. 즉 **LLM 과 일반 코드 사이의 계약(인터페이스)** 이 JSON 스키마입니다.

### 이 프로젝트의 4단 방어
1. **프롬프트 설계** – 필수 키·타입·예시를 명시, "JSON 객체 하나만, 설명·코드블록 금지" (`build_recommend_prompt`)
2. **API 의 JSON 모드** – OpenAI `response_format: json_object`, Gemini `responseMimeType: application/json`
3. **관대한 파싱** – ```json 코드펜스나 앞뒤 문장이 붙어도 `{ ... }` 부분만 꺼냄 (`extract_json`)
4. **스키마 검증 + 정규화** – 키 누락·타입 오류 검사, events 1~3개로 자르기, "강원도 강릉시" → "강릉" (`validate_recommendation`)
   → 실패하면 문제점을 알려주며 "필수 키만 다시" 1회 재요청 (`build_recommend_retry_prompt`)

### 데이터 흐름
```
LLM 텍스트 ──extract_json──► dict ──validate──► rec
rec["recommended_city"] = "제주" ──► "제주 맛집" ──► Kakao GET ──► restaurants[]
rec + restaurants ──► 리포트 프롬프트 ──► LLM POST ──► Markdown
```

## 3. 외부 API 호출의 대표 오류와 대응 원칙

**한 줄 요약**: 오류를 종류별로 나눠서, "다시 해도 안 되는 것(인증)" 은 재시도하지 말고 알려주고, "일시적인 것(네트워크/5xx)" 은 제한적으로 재시도하며, "부가 기능 실패" 는 전체를 멈추지 않는다.

| 오류 | 신호 | 원인 | 대응 원칙 | 이 프로젝트 |
|---|---|---|---|---|
| 인증 | 401, 403 (Gemini 는 400 "API key not valid") | 키 오타, 권한·서비스 미활성화 | **재시도 무의미** → 즉시 안내 | `AUTH_ERROR`, 점검 힌트 출력 |
| 쿼터 | 429 | 사용량 한도/잔액 부족 | 재시도 자제, 사용량 확인 안내 | `QUOTA_ERROR` |
| 네트워크 | 타임아웃, 연결 실패 | 인터넷·방화벽·서버 지연 | **timeout 필수**, 제한적 재시도 | LLM 60초/장소 10초, 1회 재시도 |
| 서버 | 5xx | 제공자 장애 | 잠시 후 1회 재시도 | `SERVER_ERROR` |
| 파싱 | JSON 아님, 키 누락 | LLM 형식 이탈, 응답 구조 변경 | 형식 교정 재요청 **최대 1회** | `PARSE_ERROR` |
| 빈 결과 | 200 + 0건 | 검색어가 너무 좁음 | 오류가 아님 → "데이터 없음"으로 진행 | `EMPTY_RESULT` |

### 핵심 원칙
1. **무한 재시도 금지** – 비용·쿼터를 태우고 프로그램이 멈추지 않습니다. 횟수를 정해 둡니다.
2. **우아한 성능 저하(Graceful degradation)** – 맛집은 "있으면 좋은" 데이터이므로 실패해도 리포트는 만듭니다.
   반대로 1차 추천은 다음 단계의 필수 입력이라 실패하면 중단합니다. **무엇이 필수인지** 구분하는 것이 설계입니다.
3. **기록** – 실패를 숨기지 않고 `errors` 배열(step/type/message)에 남겨 JSON 과 리포트에서 확인할 수 있게 합니다.
4. **비밀 정보 마스킹** – 에러 메시지에 키가 섞여 나올 수 있으므로 저장 전 `redact()` 로 가립니다.

## 4. API 키를 코드에 쓰지 않고 .env/환경변수로 관리하는 이유

**한 줄 요약**: 키는 "비밀번호 + 신용카드" 와 같다. 코드와 분리해야 공유해도 안전하고, 키를 바꿔도 코드를 고칠 필요가 없다.

1. **유출 방지** – 코드는 GitHub·메신저·과제 제출로 퍼집니다. 공개 저장소의 키는 자동 수집 봇이 몇 분 안에 찾아내 악용합니다.
2. **과금 사고 예방** – 유출된 LLM 키로 남이 호출하면 내 카드로 청구되거나 쿼터가 소진됩니다.
3. **교체 용이** – 키를 폐기·재발급해도 `.env` 한 줄만 바꾸면 됩니다. 코드 수정·재배포 불필요.
4. **환경 분리** – 개발/운영에서 다른 키를 같은 코드로 쓸 수 있습니다 (12-Factor App 의 "설정은 환경에").
5. **역할 분리** – 코드를 보는 사람과 키를 가진 사람을 분리할 수 있습니다.

### 이 프로젝트의 실천
- `load_dotenv()` 로 `.env` → 환경변수, `os.environ` 으로만 읽음
- `.gitignore` 에 `.env` 등록, 값이 빈 `.env.example` 만 공유
- 키가 없으면 호출 전에 즉시 종료하고 설정법 안내 (`read_keys`, `key_setup_help`)
- 로그·결과 파일 저장 전 키 마스킹 (`redact`)
